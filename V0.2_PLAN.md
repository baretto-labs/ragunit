# RAGUnit v0.2 — Roadmap

> Foundation milestone: make RAGUnit a credible measurement tool for
> LLM-as-a-judge. No domain-specific additions in this milestone.

## Status legend
- [ ] Not started
- [~] In progress
- [x] Done
- [⊘] Out of scope (do not implement in this milestone)

## Block 1 — Measurement credibility

### T1.1 Visible & overridable judge prompt
**Intent**: a score has no meaning if the user can't read the question
asked to the judge.

**Acceptance**:
- [ ] Each built-in metric (faithfulness, relevancy, factual correctness…)
  has its prompt template exposed as a public constant or builder field.
- [ ] `OllamaJudge.builder().faithfulnessPrompt(myTemplate).build()`
  compiles and is honored at runtime.
- [ ] Prompts are versioned in code (`PROMPT_V1`, `PROMPT_V2`); the
  changelog records when a prompt version is bumped.
- [ ] One unit test asserts that a custom prompt replaces the default.

### T1.2 Variance control (N-runs)
**Intent**: a single LLM-judge call has ±10–15% variance. Without
averaging, any score-based assertion is noise.

**Acceptance**:
- [ ] `.withRuns(n)` on the assertion builder runs the judge n times and
  computes mean + stddev.
- [ ] Default judge temperature is 0 (documented as the recommended
  default).
- [ ] Assertion fails if `mean < threshold` OR `stddev > maxStddev`
  (default `maxStddev = 0.15`). Failure message explicitly distinguishes
  the two cases.
- [ ] Unit test covers the unstable-judge case (mocked judge alternating
  0.9 / 0.5) → assertion fails with a "judge too unstable" message.

### T1.3 Structured JudgeResult
**Intent**: when a test fails, the user needs to see the judge's
justification and the exact prompt — not just a number.

**Acceptance**:
- [ ] `JudgeResult` is a public record with at least `score (double)`,
  `justification (String)`, `promptUsed (String)`, `rawResponse (String)`.
- [ ] AssertionError messages include the justification (first 500 chars).
- [ ] Public API exposes a way to retrieve the full `JudgeResult` for
  inspection, not only the pass/fail boolean.

## Block 2 — Generic API

### T2.1 Generic JudgeQuery
**Intent**: `RagAssert` is RAG-shaped (`forQuestion` / `givenContext`).
To support non-RAG use cases we need a lower-level entry point.

**Acceptance**:
- [ ] New public type `JudgeQuery`, built via builder, accepting arbitrary
  named inputs and a `Criterion` enum or interface.
- [ ] `Judge.evaluate(JudgeQuery)` returns a `JudgeResult`.
- [ ] `RagAssert` is refactored to construct a `JudgeQuery` under the
  hood. Public `RagAssert` API stays backward compatible with v0.1.
- [ ] At least one example in `ragunit-examples` uses `JudgeQuery`
  directly on a non-RAG case (e.g. judging a summary against a reference).

### T2.2 Deterministic assertions side-by-side
**Intent**: the right pattern is hard checks + soft judgment. Make it
first-class in the API so users don't all-in on the LLM judge.

**Acceptance**:
- [ ] `RagAssert.assertThatAnswer(text)` exposes deterministic helpers:
  `.contains(...)`, `.matches(regex)`, `.containsAll(...)`,
  `.hasMinLength(n)`.
- [ ] Deterministic helpers chain with the LLM-judged ones
  (`.evaluatedBy(...)` after a `.contains(...)`).
- [ ] No new external dependency (AssertJ, Hamcrest…) — keep it
  self-contained.

## Block 3 — Out of scope (do not implement)
- [⊘] Judge calibration tool (`JudgeCalibration`)
- [⊘] Snapshot testing
- [⊘] HTML / JUnit reporter
- [⊘] Embedding-based judge
- [⊘] Multi-judge consensus
- [⊘] Agent-specific assertions (trajectories, tool calls, diffs)
- [⊘] Any other domain-specific assertion (code, SQL, etc.)

If any of these comes up during implementation, add a one-line entry
under "Deferred ideas" and stop. Do not bundle them with v0.2.

## Release criteria
v0.2 ships when:
- All Block 1 and Block 2 tickets are `[x]`.
- Version constant bumped to `0.2.0`.
- CHANGELOG records each prompt-version bump.
- One example in `ragunit-examples` demonstrates JudgeQuery + N-runs +
  custom prompt end-to-end.

## Working rules
- One ticket = one PR.
- Update this file's status checkboxes at the start and end of each
  ticket.
- Do not add features absent from this file. If you think one is
  missing, add it under "Deferred ideas" first, then ask.
- All code, comments, commit messages in English.
