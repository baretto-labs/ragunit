# RAGUnit v0.2 — Roadmap

> Foundation milestone: make RAGUnit a credible measurement tool for
> LLM-as-a-judge. No domain-specific additions in this milestone.

## Status legend
- [ ] Not started
- [~] In progress
- [x] Done
- [⊘] Out of scope (do not implement in this milestone)

## Block 1 — Measurement credibility

### T1.1 Visible & overridable judge prompt `[x]`
**Intent**: a score has no meaning if the user can't read the question
asked to the judge.

**Acceptance**:
- [x] Each built-in metric (faithfulness, relevancy, factual correctness…)
  has its prompt template exposed as a public constant or builder field.
  → `JudgePromptLibrary.FAITHFULNESS_V1` etc., one constant per `MetricType`.
- [x] `OllamaJudge.builder().faithfulnessPrompt(myTemplate).build()`
  compiles and is honored at runtime.
- [x] Prompts are versioned in code (`PROMPT_V1`, `PROMPT_V2`); the
  changelog records when a prompt version is bumped.
  → `_V1` constants + CHANGELOG.md "Prompt versions" section.
- [x] One unit test asserts that a custom prompt replaces the default.
  → `should_useCustomFaithfulnessPrompt_when_configuredViaBuilder` and friends.

### T1.2 Variance control (N-runs) `[x]`
**Intent**: a single LLM-judge call has ±10–15% variance. Without
averaging, any score-based assertion is noise.

**Acceptance**:
- [x] `.withRuns(n)` on the assertion builder runs the judge n times and
  computes mean + stddev. → `AnswerAssert` and `ContextAssert`, backed by
  `ScoreStatistics` (population stddev).
- [x] Default judge temperature is 0 (documented as the recommended
  default). → `OllamaJudge` sends `temperature: 0`; `builder().temperature(x)`
  to override; documented in `docs/variance-control.md`.
- [x] Assertion fails if `mean < threshold` OR `stddev > maxStddev`
  (default `maxStddev = 0.15`). Failure message explicitly distinguishes
  the two cases. → `withMaxStddev(x)`, default `ScoreStatistics.DEFAULT_MAX_STDDEV`.
- [x] Unit test covers the unstable-judge case (mocked judge alternating
  0.9 / 0.5) → assertion fails with a "judge too unstable" message.
  → `should_failWithUnstableMessage_when_judgeAlternatesHighAndLowScores`.

### T1.3 Structured JudgeResult `[x]`
**Intent**: when a test fails, the user needs to see the judge's
justification and the exact prompt — not just a number.

**Acceptance**:
- [x] `JudgeResult` is a public record with at least `score (double)`,
  `justification (String)`, `promptUsed (String)`, `rawResponse (String)`.
  → plus `model (String)`; built from `Verdict` which now carries the exchange.
- [x] AssertionError messages include the justification (first 500 chars).
  → appended as `— judge justification: "…"` with 500-char truncation.
- [x] Public API exposes a way to retrieve the full `JudgeResult` for
  inspection, not only the pass/fail boolean.
  → `lastJudgeResult()` on `AnswerAssert` and `ContextAssert`, populated on
  pass and on failure.

## Block 2 — Generic API

### T2.1 Generic JudgeQuery `[x]`
**Intent**: `RagAssert` is RAG-shaped (`forQuestion` / `givenContext`).
To support non-RAG use cases we need a lower-level entry point.

**Acceptance**:
- [x] New public type `JudgeQuery`, built via builder, accepting arbitrary
  named inputs and a `Criterion` enum or interface.
  → `Criterion` interface (+ `Criterion.of(...)`); `MetricType implements Criterion`.
- [x] `Judge.evaluate(JudgeQuery)` returns a `JudgeResult`.
  → new `Judge` interface; `RagJudge extends Judge` with default dispatch of
  built-in metric criteria to the typed methods (existing impls work unchanged).
- [x] `RagAssert` is refactored to construct a `JudgeQuery` under the
  hood. Public `RagAssert` API stays backward compatible with v0.1.
  → 12 of 13 metrics flow through JudgeQuery + dispatch (TOOL_TRAJECTORY and
  the factual-correctness selectors stay typed: no faithful flat encoding).
- [x] At least one example in `ragunit-examples` uses `JudgeQuery`
  directly on a non-RAG case (e.g. judging a summary against a reference).
  → `SummaryJudgeQueryExampleTest` (summary vs source, summary vs reference).

### T2.2 Deterministic assertions side-by-side `[x]`
**Intent**: the right pattern is hard checks + soft judgment. Make it
first-class in the API so users don't all-in on the LLM judge.

**Acceptance**:
- [x] `RagAssert.assertThatAnswer(text)` exposes deterministic helpers:
  `.contains(...)`, `.matches(regex)`, `.containsAll(...)`,
  `.hasMinLength(n)`.
  → plus a `RagAssert.assertThatAnswer(String)` overload for plain text.
- [x] Deterministic helpers chain with the LLM-judged ones
  (`.evaluatedBy(...)` after a `.contains(...)`).
  → both orders tested; deterministic checks make no LLM call and skip reporters.
- [x] No new external dependency (AssertJ, Hamcrest…) — keep it
  self-contained.

## Block 3 — Out of scope (do not implement)
- [⊘] Judge calibration tool (`JudgeCalibration`)
- [⊘] Snapshot testing
- [⊘] HTML / JUnit reporter
- [⊘] Embedding-based judge
- [⊘] Multi-judge consensus
- [⊘] Agent-specific assertions (trajectories, tool calls, diffs)
- [⊘] Any other domain-specific assertion (code, SQL, etc.)

If any of these comes up during implementation, add a one-line entry
under "Deferred ideas" and stop. Do not bundle them with v0.2.

## Release criteria
v0.2 ships when:
- [x] All Block 1 and Block 2 tickets are `[x]`.
- [x] Version constant bumped to `0.2.0` (all Maven modules).
- [x] CHANGELOG records each prompt-version bump (all prompts at V1,
  wording identical to v0.1 — scores comparable).
- [x] One example in `ragunit-examples` demonstrates JudgeQuery + N-runs +
  custom prompt end-to-end. → `MeasurementFoundationExampleTest`.
